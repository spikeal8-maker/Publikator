# Publikator 0.8.0-rc.1

Статус: **release candidate, не stable V1**.

## Цель релиза

`0.8.0-rc.1` не расширяет Publikator новой инфраструктурой. Его задача — сделать техническую готовность к стабильному V1 измеримой и не позволить перепутать внутренние automated checks с реальной проверкой внешних соцсетей.

## Основные изменения

### Release-readiness gate

Добавлен authenticated endpoint:

```text
GET /api/release-readiness
```

Он возвращает отдельные признаки:

- `automatedReady` — локальные runtime/CI условия позволяют переходить к live acceptance;
- `stableV1Ready` — в RC намеренно остаётся `false`;
- `automatedBlockers` — список технических блокеров;
- `checks` — PASS/WARN/BLOCK/EXTERNAL_REQUIRED;
- `liveAcceptance` — обязательный ручной gate Telegram/VK/MAX/Instagram;
- полный diagnostics snapshot как evidence.

JSON-отчёт можно скачать:

```text
GET /api/release-readiness/report.json
```

### Что блокирует automated RC gate

- SQLite `quick_check != ok`;
- `journal_mode != wal`;
- missing media или несовпадение размера media SQLite↔disk;
- критически мало свободного места;
- активный `RECOVERY_NEEDED`;
- MAX/Instagram активны, но `PUBLIC_BASE_URL` не готов как HTTPS;
- активный maintenance;
- последняя необработанная ошибка scheduler;
- отсутствует хотя бы один полный `.tgz` backup bundle;
- версия приложения не определяется.

Orphan media, низкий запас места и отдельные эксплуатационные состояния могут давать WARN без автоматического блокирования.

### Web UI

В меню добавлен раздел **Готовность V1**:

- статус automated RC gate;
- список технических блокеров;
- отдельная карточка обязательного live acceptance;
- карточки всех release checks;
- скачивание JSON evidence.

### Безопасность release-процесса

Mock publisher, HTTP E2E и CI не могут перевести `stableV1Ready` в `true`. Реальное поведение Telegram/VK/MAX/Instagram требует ручной проверки по `docs/LIVE_INTEGRATION_CHECKLIST.md`.

## Что уже входит из V0.7

RC построен поверх V0.7 operational hardening:

- duplicate-safe `RECOVERY_NEEDED`;
- явные операторские recovery-развязки;
- runtime diagnostics;
- scheduler telemetry;
- event/backup retention;
- mock publisher E2E;
- authenticated HTTP CRUD E2E;
- CSV/XLSX regression;
- полный Docker/backup/restore CI.

## Совместимость

- production topology остаётся одним Docker-контейнером;
- SQLite/WAL и локальное media storage сохраняются;
- новая обязательная runtime БД не появляется;
- Redis/RabbitMQ/n8n/worker не добавляются;
- `APP_MASTER_KEY` менять нельзя;
- destructive migration в `0.8.0-rc.1` не добавляется.

Подробный upgrade/rollback: `docs/UPGRADE.md`.

## Automated acceptance

Для PR/release-head должны быть зелёными минимум:

1. общий CI — TypeScript, frontend syntax, legacy migration, production Docker, runtime/media/full restore;
2. Content plan CI — настоящий CSV/XLSX round-trip;
3. Ops hardening CI — mock publisher/recovery/scheduler/retention/diagnostics и authenticated HTTP CRUD;
4. Release candidate CI — readiness E2E с проверкой блокеров и скачиваемого report.

## Что намеренно не считается завершённым

До stable V1 остаётся внешний release gate:

- Telegram live acceptance;
- VK live acceptance;
- MAX live acceptance;
- Instagram live acceptance;
- контролируемый live-сценарий `RECOVERY_NEEDED`;
- финальный backup/restore acceptance на release commit.

До выполнения этого списка релиз остаётся prerelease независимо от того, насколько зелёным является CI.
