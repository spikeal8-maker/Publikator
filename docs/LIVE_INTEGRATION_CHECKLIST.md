# Live integration checklist перед стабильным V1

Этот документ используется только для ручной проверки реальных подключений Telegram, VK, MAX и Instagram перед выпуском стабильного V1. Mock/E2E тесты не заменяют эту проверку, потому что внешние API, права аккаунтов, модерация и сетевые ограничения меняются независимо от Publikator.

Дата последней сверки checklist: **2026-09-10**.

## Общие условия

Перед live-проверкой:

1. Развернуть тот же Docker image/commit, который планируется выпускать.
2. Открыть раздел **Диагностика** и убедиться:
   - SQLite `quick_check = ok`;
   - `journal_mode = wal`;
   - отсутствуют потерянные media и size mismatch;
   - scheduler не показывает последнюю необработанную ошибку;
   - для MAX/Instagram `PUBLIC_BASE_URL` является публичным HTTPS URL;
   - нет необработанных `RECOVERY_NEEDED`, не относящихся к текущему тесту.
3. Создать отдельный тестовый проект и отдельный тестовый аккаунт каждой площадки, если это возможно.
4. Не использовать основной боевой пост для destructive/retry сценариев.
5. Создать полный backup bundle непосредственно перед live acceptance.
6. Записать commit SHA, время теста, площадку, account name и результат в журнал релиза.

## Единый набор тестовых публикаций

Для каждой площадки проверить минимум:

1. Одна JPEG-картинка + короткий текст.
2. Текст с кириллицей, emoji, URL и переносами строк.
3. Отдельный `override_text` для площадки: опубликованный текст должен отличаться от базового именно так, как показано в preview.
4. Несколько изображений в поддерживаемом платформой количестве и в заданном `sort_order`.
5. Ручной `publish-now`.
6. `AT` с датой на несколько минут вперёд.
7. `QUEUE` через отдельный тестовый slot.
8. После успешной публикации убедиться, что повторное редактирование текста/targets/media заблокировано.
9. Проверить `external_id`; если adapter возвращает публичную ссылку, проверить и `external_url`.
10. Проверить журнал: `publish_started` → `publish_succeeded` без неожиданных повторов.

## Telegram

Перед тестом подключения:

- бот добавлен в нужный канал/чат;
- бот имеет права администратора/создателя, необходимые для публикации;
- `Bot token` относится именно к этому боту;
- `chat_id`/username соответствует выбранному каналу.

Acceptance:

1. В UI выполнить **Проверить подключение** и получить успешные `getMe → getChat → getChatMember`.
2. Опубликовать одиночное изображение.
3. Опубликовать media group из нескольких изображений и сверить порядок.
4. Проверить длинный текст, при котором caption уже недостаточен: media и отдельное текстовое сообщение не должны дублироваться.
5. Проверить русские символы, emoji и URL.
6. После теста удалить тестовые публикации вручную с площадки, если они больше не нужны.

Официальная документация: `https://core.telegram.org/bots/api`.

## VK

Перед тестом подключения:

- token действительно имеет права для нужного сообщества;
- `Group ID` соответствует сообществу;
- API version указана явно и поддерживается текущим VK API.

Acceptance:

1. В UI выполнить **Проверить подключение**: `photos.getWallUploadServer` должен успешно вернуть upload URL.
2. Опубликовать JPEG и сверить текст/изображение на стене.
3. Опубликовать несколько изображений и сверить порядок.
4. Повторно инициировать тест с тем же `post.id` в контролируемом сценарии и убедиться, что VK `guid` защищает от дублирования `wall.post` там, где это поддерживается API.
5. Отдельно проверить тип token: неподходящий community token не должен ошибочно считаться рабочим, если upload API требует другой тип доступа.

Официальную актуальную документацию VK API необходимо сверять непосредственно перед релизом, поскольку требования к токенам и версиям API могут меняться.

## MAX

Перед тестом подключения:

- используется актуальный домен `platform-api2.max.ru`;
- access token передаётся через `Authorization`, а не query string;
- бот является владельцем/администратором целевого чата/канала с правом записи;
- `PUBLIC_BASE_URL` доступен с внешнего интернета по HTTPS без VPN/локального DNS;
- `/public-media/...` возвращает изображение без авторизации.

Acceptance:

1. В UI выполнить **Проверить подключение** и подтвердить успешные `GET /me` и проверку membership/permissions.
2. Проверить одиночное JPEG через публичный URL.
3. Проверить несколько изображений в одном сообщении в пределах текущего adapter-limit.
4. Из внешней сети отдельно открыть один из media URL, который будет передан MAX.
5. Проверить, что изображение не превышает ограничения MAX, используемые preflight.
6. Проверить реальный ответ `POST /messages`, сохранить внешний ID и при наличии публичную ссылку.

По документации MAX, актуальной на 2026-09-10, для новых интеграций используется `platform-api2.max.ru`; изображения могут передаваться внешним URL, а upload API ограничивает изображение 50 МБ и 7680×7680 px. Перед каждым стабильным релизом сверять `https://dev.max.ru/docs-api`, changelog и методы `/uploads` и `/messages`.

## Instagram

Перед тестом подключения:

- используется профессиональный Instagram account, который поддерживает publishing API;
- access token и Instagram User ID относятся к одной интеграции;
- Graph/Instagram API version указана явно и ещё поддерживается Meta;
- `PUBLIC_BASE_URL` является публичным HTTPS;
- Meta может скачать media URL без cookie/авторизации.

Acceptance:

1. В UI выполнить **Проверить подключение** и подтвердить выбранный Instagram account.
2. Опубликовать одиночный JPEG.
3. Опубликовать carousel из 2 изображений.
4. Опубликовать carousel из 10 изображений.
5. Сверить порядок carousel с `media.sort_order`.
6. Сверить кадрирование и влияние первого изображения на carousel.
7. Убедиться, что Publikator не принимает неподдерживаемый media-set в `READY`.
8. Проверить container creation и `media_publish` как единый сценарий без повторного `media_publish` после неопределённого результата.

Актуальная официальная Meta/Postman документация на 2026-09-10 указывает, что media при API publishing должна быть доступна на публичном сервере, JPEG поддерживается для image publishing, а carousel может содержать до 10 элементов. Перед релизом обязательно повторно сверять текущую Instagram API collection Meta.

## RECOVERY_NEEDED — обязательный live-тест

Этот тест проводить только на отдельном тестовом аккаунте/канале.

1. Искусственно создать сетевой сбой **после начала внешнего POST**, если это можно сделать контролируемо без риска боевых публикаций.
2. Убедиться, что target переходит в `RECOVERY_NEEDED`.
3. Убедиться, что обычная кнопка `Повторить` недоступна и generic retry API возвращает ошибку.
4. Вручную проверить внешнюю площадку.
5. Если публикация существует:
   - выбрать **Публикация найдена**;
   - при возможности записать external ID/URL;
   - убедиться, что внешний POST повторно не вызывается;
   - target должен стать `PUBLISHED`.
6. Если публикации точно нет:
   - выбрать **Публикации точно нет**;
   - target должен стать `FAILED`;
   - только после этого вручную нажать обычный retry;
   - убедиться, что выполняется ровно один новый внешний POST.
7. Проверить события `publish_recovery_confirmed_published` или `publish_recovery_confirmed_absent`.

## Backup/restore acceptance

После live-публикаций:

1. Создать новый полный backup bundle.
2. Скачать bundle и проверить, что он ненулевого размера.
3. На отдельной тестовой установке с тем же `APP_MASTER_KEY` выполнить restore.
4. После рестарта проверить:
   - проекты;
   - аккаунты;
   - посты и target states;
   - platform overrides;
   - media и их порядок;
   - журнал событий;
   - экран диагностики.
5. Убедиться, что restore с другим `APP_MASTER_KEY` блокируется до замены данных.

## Критерий выпуска V1

Стабильный V1 можно выпускать только если одновременно:

- все automated CI зелёные на release commit;
- все четыре площадки, заявленные как поддерживаемые в релизе, прошли live checklist либо явно отключены/помечены как неподтверждённые;
- нет необработанных `RECOVERY_NEEDED` из acceptance;
- диагностика не содержит ошибок SQLite/media/public URL;
- создан и проверен полный backup release-state;
- зафиксированы commit SHA и дата live acceptance.
