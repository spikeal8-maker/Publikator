# Publikator — каноническое функциональное описание интерфейса и автоматизации

Статус: **NORMATIVE PRODUCT / OPERATOR UI CONTRACT**

Версия документа: `1.0`

Назначение: этот документ задаёт каноническую продуктовую модель пользовательских страниц Publikator, их функционал, кнопки, состояния, подсказки, переходы и автоматизацию. Он не описывает историческую структуру текущего frontend-кода и не должен копировать технические внутренности в пользовательский интерфейс.

Этот документ подчиняется `VNEXT_TECHNICAL_SPEC.md`, `ARCHITECTURE.md` и `DEVELOPMENT_RULES.md`. Если возникает конфликт с доменными или safety-invariants, действует более высокий по приоритету документ.

---

# 0. Базовые принципы

## 0.1 Главная пользовательская задача

Publikator должен позволять оператору пройти полный путь:

```text
подключить площадки и источники
→ получить/создать контент
→ проверить и подготовить
→ назначить время или очередь
→ опубликовать вручную или автоматически
→ увидеть результат
→ безопасно разобрать ошибки
```

Пользовательский интерфейс MUST объяснять не внутренние состояния системы, а:

- что происходит;
- что нужно сделать;
- что произойдёт после действия;
- почему действие недоступно;
- безопасно ли повторять действие.

## 0.2 Запрещённые технические термины в обычном UI

Оператор не обязан видеть без необходимости:

```text
READY
QUEUE
AT
RECOVERY_NEEDED
PublicationUnit
content_version
ready_revision_id
source SHA
BUILD_SHA
schema version
checkpoint ID
```

Они допустимы только в `Диагностика → Технические сведения`, журнале технических деталей или developer tooling.

Канонические пользовательские формулировки:

| Внутреннее понятие | UI-текст |
|---|---|
| `DRAFT` | Черновик |
| `READY` | Готово к публикации |
| `PUBLISHING` | Публикуется |
| `PUBLISHED` | Опубликовано |
| `PARTIAL` | Опубликовано частично |
| `FAILED` | Ошибка публикации |
| `RECOVERY_NEEDED` | Требуется проверка результата |
| `MANUAL` | Вручную |
| `AT` | В конкретное время |
| `QUEUE` | Автоматически из очереди |
| `FEED` | Пост |
| `SHORT` | Короткое видео |
| `STORY` | История |

## 0.3 Один источник истины

Frontend MUST использовать единые словари для:

- routes;
- пользовательских статусов;
- publication kinds/formats;
- platform names;
- capability labels;
- подсказок validation/preflight.

Нельзя иметь отдельные несовпадающие словари для Dashboard, Calendar, Library, Content и Editor.

## 0.4 Навигация

Каноническая навигация:

### Работа

- Обзор
- Публикации
- Календарь
- Медиатека
- Шаблоны
- Проекты

### Подключения

- Соцсети
- Источники

### Автоматизация

- Автоматизация

### Система

- Журнал
- Резервные копии
- Диагностика
- Настройки

Текущие legacy-маршруты MAY временно сохраняться как aliases при миграции, но канонические продуктовые названия выше являются целевыми.

# 1. Общая оболочка приложения

## 1.1 Верхняя панель

Постоянно содержит:

1. **Переключатель проекта** — `Все проекты` / конкретный проект.
2. **Глобальный поиск** — MAY появиться после реализации единого search API.
3. **`+ Новая публикация`** — главное создание контента.
4. **Уведомления** — только actionable события.
5. **Состояние системы** — зелёный/жёлтый/красный индикатор.
6. Меню пользователя/администратора.

### Подсказки

**Все проекты**
> Фильтрует публикации, календарь, медиатеку и автоматизацию по выбранному проекту.

**+ Новая публикация**
> Создать новый материал вручную. После сохранения можно добавить медиа, площадки и время публикации.

**Состояние системы**
> Показывает, есть ли проблемы с Publikator, площадками, источниками или автоматизацией.

## 1.2 Глобальные loading/error/empty states

Каждая страница MUST иметь:

- loading state без скачка layout;
- empty state с объяснением следующего действия;
- inline error с кнопкой повторной загрузки, если повтор безопасен;
- disabled action с пояснением причины.

Нельзя показывать просто `HTTP 409`, `API error` или `undefined`.

# 2. Обзор

## 2.1 Назначение

Ответить на вопросы:

1. Что должно выйти сегодня?
2. Что выйдет в ближайшее время?
3. Какие материалы ещё не готовы?
4. Где требуется решение оператора?

## 2.2 Компоновка

### Блок A — показатели

Карточки:

- **Сегодня** — публикации на сегодня;
- **7 дней** — публикации ближайших семи дней;
- **Требуют внимания** — материалы, которые оператор должен подготовить;
- **Проблемы** — ошибки публикации или неизвестный внешний результат.

Клик по карточке MUST вести на соответствующий фильтр в Публикациях/Календаре.

### Блок B — Ближайшие публикации

Каждая строка:

```text
14:00 · ASA Lab · Telegram + VK
Новый урок Arduino
```

Кнопка: **Открыть**.

### Блок C — Требуют внимания

Показывать конкретную причину:

- Не выбрана площадка.
- Нет обязательного медиа.
- Не назначено время.
- Материал не прошёл редакционную проверку.
- Подключение площадки требует повторной проверки.

Кнопка: **Исправить**.

### Блок D — Проблемы

Пример:

> Instagram не подтвердил результат отправки. Повторная публикация может создать дубликат.

Кнопка: **Разобраться**.

Generic `Повторить` в unknown-outcome состоянии запрещён.

### Блок E — Источники

Для каждого источника:

```text
Google Sheets · ASA Social Plan
Последняя синхронизация: 11:42
Следующая проверка: 11:57
✓ Работает
```

или:

```text
⚠ 3 строки требуют решения
```

Кнопка: **Открыть источник**.

## 2.3 Empty state первого запуска

Если система пуста:

> Настройте Publikator

Чеклист:

1. Создайте проект.
2. Подключите хотя бы одну соцсеть.
3. Создайте публикацию или подключите источник.
4. Проверьте первую публикацию.
5. При необходимости включите автоматизацию.

# 3. Публикации

## 3.1 Назначение

Единый рабочий список канонических публикаций. Это не медиатека файлов.

## 3.2 Верхняя зона

- `+ Новая публикация`
- Поиск по заголовку, тексту, проекту, площадке.
- Фильтры:
  - Все;
  - Черновики;
  - Готовы;
  - Запланированы;
  - Опубликованы;
  - Проблемы.
- Вторичный scope:
  - Активные;
  - Архив;
  - Корзина.

## 3.3 Desktop-таблица

Колонки:

| Колонка | Содержание |
|---|---|
| Публикация | thumbnail/poster + заголовок + фрагмент текста |
| Проект | project name |
| Площадки | конкретные accounts |
| Формат | Пост / История / Короткое видео |
| Публикация | Вручную / В конкретное время / Автоматически |
| Когда | дата/время либо «из очереди» |
| Состояние | человекочитаемый status |
| Действия | `…` |

## 3.4 Mobile

Каждая публикация отображается карточкой:

```text
[thumbnail] Заголовок
Проект: ASA Lab
Площадки: Telegram · VK
Формат: Пост · Изображение
Когда: Сегодня 14:00
Состояние: Готово к публикации
[Открыть]
```

Горизонтальный scroll всей страницы запрещён.

## 3.5 Меню действий

### Черновик

- Открыть
- Дублировать
- Переместить в проект
- Архивировать
- В корзину

### Готово

- Открыть
- Опубликовать сейчас
- Изменить время
- Дублировать
- Архивировать

### Опубликовано

- Открыть результат
- Дублировать
- Архивировать

### Ошибка/неизвестный результат

- Разобраться
- Открыть журнал

Generic retry показывается только когда backend явно классифицировал повтор как безопасный.

## 3.6 Подсказки статусов

**Черновик**
> Материал ещё можно свободно редактировать.

**Готово к публикации**
> Все обязательные данные заполнены, а выбранные площадки прошли проверку.

**Запланировано**
> Публикация имеет точное время запуска.

**Опубликовано**
> Площадка подтвердила внешний результат публикации.

**Требуется проверка результата**
> Publikator не может безопасно определить, была ли публикация создана. Не повторяйте отправку без проверки.

# 4. Редактор публикации / Content Inspector

Редактор SHOULD быть отдельным route или large drawer. На mobile MUST быть full-screen.

## 4.1 Шаг 1 — Основное

Поля:

### Проект

Подсказка:
> Определяет, к какому направлению относится публикация и какие defaults/правила к ней применяются при создании.

### Заголовок

Подсказка:
> Внутреннее название материала. Не все площадки показывают его пользователям.

### Основной текст

Rich-text editor использует canonical portable model, а не raw platform Markdown/HTML.

### Когда публиковать

Варианты:

- Вручную
- В конкретное время
- Автоматически из очереди

**Вручную**
> Материал будет опубликован только по явной команде оператора.

**В конкретное время**
> Publikator опубликует материал в указанный момент, если он останется готовым и площадка доступна.

**Автоматически из очереди**
> Материал может быть выбран подходящим правилом автоматизации после перехода в состояние «Готово к публикации».

При выборе конкретного времени показываются:

- дата;
- время;
- часовой пояс.

## 4.2 Шаг 2 — Медиа

Drop zone:
> Перетащите изображения или видео сюда

Кнопки:

- Добавить изображение
- Добавить видео

Карточка файла показывает:

- preview/poster;
- оригинальное имя;
- MIME/type;
- размер;
- width × height;
- duration для видео;
- sort order.

Действия:

- Переместить левее/правее или drag reorder;
- Скачать;
- Удалить.

Подсказка:
> Publikator проверит ограничения выбранных площадок перед переводом материала в готовое состояние.

## 4.3 Шаг 3 — Площадки

Явный checkbox list конкретных accounts:

```text
☑ Telegram — Основной канал
☑ VK — ASA Lab
☐ MAX — Школьный канал
☐ Instagram — Main Professional
```

Если площадка не подключена:
> + Подключить Telegram

Подсказка:
> Выберите конкретные подключения, куда должна уйти эта публикация.

## 4.4 Шаг 4 — Варианты по площадкам

По умолчанию:
> Используется основной текст.

Для каждой площадки MAY быть отдельный override.

Кнопки:

- Настроить отдельно
- Использовать основной текст
- Сохранить вариант

Preview MUST быть помечен как ориентировочный:
> Финальный внешний вид определяется интерфейсом площадки.

## 4.5 Нижняя action bar

### Новый материал

- Сохранить черновик
- Закрыть

После первого сохранения появляются Медиа и Площадки.

### Черновик

- Сохранить
- Готово к публикации
- Закрыть

### Готовый

- Сохранить допустимые изменения, если они не нарушают lifecycle
- Опубликовать сейчас
- Изменить расписание

### Published / immutable publication history

Редактирование опубликованного snapshot запрещено. Доступны:

- Открыть результат
- Дублировать
- Архивировать

## 4.6 `Готово к публикации`

Перед действием система MUST выполнить единый preflight:

- редакционная policy;
- target selection;
- media/format compatibility;
- platform capability;
- schedule validity;
- immutable ready revision.

Подсказка:
> Publikator проверит обязательные поля, медиа, площадки и ограничения платформ. Внешняя публикация при этом не выполняется.

# 9. Соцсети

## 9.1 Назначение

Подключение конкретных внешних destinations/accounts.

## 9.2 Доступные платформы

Карточки:

- Telegram
- VK
- MAX
- Instagram

Кнопка каждой: **Подключить**.

## 9.3 Подключённые площадки

Карточка:

```text
Telegram
Основной канал
@asa_lab

```

Кнопки:

- Проверить
- Настройки
- `…` → Отключить / Удалить

## 9.4 Общий connect contract

Сохранить подключение нельзя до успешной проверки credentials + destination.

Канонический flow:

```text
ввести credentials
→ указать destination
→ Проверить подключение
→ показать identity → destination
→ только после этого разрешить Сохранить подключение
```

Изменение любого credential/destination после проверки инвалидирует verified state.

## 9.5 Telegram

Поля:

- Название подключения
- Токен бота
- Куда публиковать

Placeholder:
> @my_channel или https://t.me/my_channel

Подсказка токена:
> Токен из BotFather. Он хранится в Publikator в зашифрованном виде.

Подсказка destination:
> Укажите канал или чат. Бот должен иметь право публиковать туда.

Кнопка:
- Проверить подключение

Успех:
> Подключение работает. @asa_bot → ASA Lab

Кнопка после проверки:
- Сохранить подключение

## 9.6 VK

Поля:

- Название
- Access token
- Группа / group id / допустимый URL

Подсказка:
> Токен должен иметь права, достаточные для публикации от имени выбранной группы.

## 9.7 MAX

Поля:

- Название
- Token
- ID чата/канала

## 9.8 Instagram

Поля:

- Название
- Access token
- Instagram Professional User ID
- Graph API version, если её не фиксирует backend

## 9.9 Capability display

Для каждого подключения SHOULD показываться не raw flags, а:

```text
Посты: поддерживаются
Видео: поддерживаются / не проверены
Истории: поддерживаются / не проверены
Короткие видео: поддерживаются / не проверены
```

Capability нельзя включать только потому, что код существует; требуется нормативное API/тест/live acceptance согласно `VNEXT_TECHNICAL_SPEC.md`.

## Создание правила

### Шаг 1 — Когда

Поддерживаемые canonical trigger kinds:

- По расписанию
- Вручную

Дополнительные trigger kinds, например «после sync», вводятся отдельным implementation checkpoint и не должны превращать Publikator в generic workflow engine.

Для расписания:

- дни недели;
- время;
- timezone.

### Шаг 2 — Что выбирать

- Project
- Только публикации со статусом «Готово к публикации»
- Optional source/tag filters после реализации соответствующего backend contract
- Maximum publications per run

Подсказка:
> Ограничивает количество внешних публикаций за один запуск правила.

### Шаг 3 — Что сделать

Для текущего publication automation:

- взять следующий готовый материал;
- опубликовать через обычный publisher pipeline.

Автоматизация MUST переиспользовать тот же preflight, immutable revision, atomic target claim и recovery semantics, что и ручная публикация.

### Шаг 4 — Безопасность

Неотключаемые safety rules:

- не повторять уже подтверждённо опубликованные units;
- остановиться при unknown external outcome;
- не публиковать материал, который перестал быть READY;
- не публиковать через disabled/invalid account;
- не обходить platform capability/preflight.

# 11.3 Автоматизация источников

## Цель

Регулярно обнаруживать изменения внешнего источника без ручного открытия страницы.

## Google Sheets polling

После реализации scheduler contract connector MAY иметь:

- Включить автоматическую проверку
- Интервал: 5 / 15 / 30 / 60 минут
- Последняя проверка
- Следующая проверка
- Последний результат

### Безопасный pipeline

```text
poll source
→ Preview
→ если snapshot стабилен и нет blocking conflict/error
→ optional auto-Apply безопасных NEW/UPDATE
→ создать/обновить только editable content
→ optional Trusted-source Auto Ready через тот же immutable revision + platform preflight gate
→ при любом READY-block оставить материал DRAFT и записать причину
→ отдельная publication automation работает только с READY content
```

Критический invariant:

> Ingestion не выполняет внешний publish напрямую.

Auto-Apply MAY создавать/обновлять DRAFT/редактируемый content согласно import contract, но не должен обходить review/preflight/READY.

## Trusted-source Auto Ready — CP2-007C

Auto Ready является отдельной approval-policy функцией и MAY быть включён только явно для доверенного Google Sheets connector.

Обязательные invariants:

- default: OFF;
- требует включённый Auto Apply;
- работает только после успешного Auto Apply без `CONFLICT/ERROR`;
- `imported_content_version` должен совпадать с `content_version`;
- обязательны media и хотя бы одна активная выбранная площадка;
- создаётся immutable content revision;
- выполняется тот же platform capability/preflight, что при ручной кнопке «Готово»;
- при любом отказе материал остаётся `DRAFT`, причина фиксируется в журнале;
- Auto Ready не вызывает publisher и не является внешней публикацией.

Изменение ранее READY материала через source сначала инвалидирует approval и возвращает материал в DRAFT; новая ревизия должна заново пройти Auto Ready gate.


## Настройки source automation

- Автоматическая проверка: on/off
- Интервал
- При безопасных изменениях:
  - Только уведомить
  - Автоматически применить новые/изменённые editable строки
- Trusted-source Auto Ready: on/off; доступен только при включённом Auto Apply
- При конфликте:
  - Остановиться и уведомить

Default:
> Только уведомить; Auto Apply OFF; Auto Ready OFF

# 11.4 Write-back в Google Sheets

### CP2-008A — фактический результат публикации

При включённом write-back входные колонки остаются A:U. Publikator владеет служебными колонками V:AD:

- V:Y — результат Preview/Apply импорта;
- Z `publication_status`;
- AA `editorial_stage`;
- AB `published_at`;
- AC `external_urls` — JSON по подтверждённым внешним результатам;
- AD `publication_error`.

Publication write-back MUST быть идемпотентным и best-effort: ошибка Google Sheets не меняет канонический статус уже выполненной публикации и не запускает повтор внешнего publish.


Optional write-back MAY содержать:

- publikator id;
- sync status;
- editorial stage;
- publication status;
- фактическое время;
- published_at;
- external URLs;
- last error.

UI-настройки:

- Записывать состояние синхронизации
- Записывать состояние публикации
- Записывать дату публикации
- Записывать внешние ссылки
- Записывать ошибку

Правило:

> Ошибка write-back не отменяет уже подтверждённую внешнюю публикацию.

UI пример:

> ✓ Публикация отправлена.  
> ⚠ Не удалось записать результат обратно в Google Sheets.

Безопасная кнопка:
- Повторить запись статуса

Она повторяет только write-back, а не публикацию.

# 20. Frontend implementation constraints

Этот документ определяет функциональный результат, а не конкретный framework. Однако новый UI MUST стремиться к единой архитектуре:

# 23. Неизменяемые safety-invariants

Независимо от UI:

- external publish выполняется только через canonical publisher pipeline;
- publisher читает immutable ready revision;
- atomic target/unit claim обязателен;
- `RECOVERY_NEEDED` автоматически не повторяется;
- already published PublicationUnits не повторяются;
- source Preview не меняет canonical DB;
- source Apply не публикует внешне;
- Google Sheets не становится master DB;
- удаление строки источника не означает delete;
- automation не обходит platform capability/preflight;
- credentials не возвращаются в frontend после сохранения;
- backup/restore safety contract остаётся обязательным.

Этот документ является каноническим функциональным контрактом операторского интерфейса Publikator и должен использоваться как источник истины при дальнейшей разработке страниц, автоматизации, подсказок и browser acceptance.
