Устаревшие продуктовые указания маркируются либо заменяются; доменные, security и publication invariants не ослабляются. Не приступать к миграции UI при противоречии нормативных документов. ## 0.1 Повторный продуктовый анализ

1.0 предлагала семь разделов и отдельный Обзор. Риск — снова получить административную систему с дублирующими страницами. 1.1 сокращает постоянную навигацию до пяти рабочих разделов + Настройки; календарь становится стартовым экраном с задачами и ближайшими публикациями. Дополнительные панели открываются по запросу. ИИ доступен внутри редактора. Уточнены связанные материалы, согласование, ошибки и расходы моделей, самостоятельные полезные выпуски и измеримые критерии.

[Интерактивный прототип](prototypes/publikator-2/index.html) — автономный HTML с демонстрационными данными. Открывать локально в браузере. Это не runtime Publikator, он не обращается к сети, не вызывает ИИ/MCP и не публикует. Его задача — проверка компоновки и переходов.

Проверены public/index.html, calendar-v3.css, composer-layout-v1.css, assistant.css, src/http/calendar.ts, src/owner-ai-providers.ts на исходном baseline. Многочисленные переопределения important и отдельные токены/оболочка чата подтверждают фрагментацию архитектуры UI, но не являются измерением реальной производительности или скриншотами production. Фактический визуальный baseline фиксируется в P2-00; не проводить ещё один общий аудит вместо реализации.

## 1. Зачем существует Publikator

Единое рабочее место владельца одного или нескольких проектов для ведения социальных сетей. Пользователь формулирует идеи, планирует публикации, создаёт или импортирует текст, изображения и видео, проверяет внешний вид на каждой площадке, согласует и публикует автоматически в заданное время; затем видит реальный результат и статистику. Внутренний ИИ и внешний ChatGPT/MCP являются другими входами в те же функции, а не самостоятельными продуктами.

Главные пользовательские сценарии:
- «Написать текст, добавить фотографии/видео, выбрать получателей, отправить или запланировать».
- «Составить контент-план на неделю/месяц, разложить разные форматы по календарю и постепенно подготовить их».
- «Попросить ИИ написать пост, создать картинку/видео, сохранить черновик, проверить и запланировать».
- «Работать из внешнего ChatGPT или другого совместимого MCP-клиента без обязательного открытия сайта».
- «Понять, что уже отправилось, что ждёт согласования и что не удалось; исправить конкретную причину».
- «Один раз подключить соцсети, модели, источники и внешних помощников, затем работать без технических действий».

Пользователю не показывать обязательные технические сущности вроде READY, OAuth scope, target rendition, SQLite, scheduler tick, idempotency key. Диагностика доступна владельцу по запросу. Не упрощать безопасность вместе с интерфейсом.

## 3. Информационная архитектура

### 3.1 Постоянная навигация: пять рабочих разделов + настройки

| Раздел | Когда нужен | Представления и действия | Целевой маршрут |
|---|---|---|---|
| Календарь | Начать день, подготовить план, увидеть задачи | Неделя, месяц, день, список; выбранный день; очередь внимания | /calendar |
| Публикации | Найти, проверить и исправить материал | Все, черновики, согласование, план, опубликовано, ошибки | /content |
| Медиатека | Найти или создать медиа | Файлы, шаблоны, импорт и генерация | /library |
| ИИ-помощник | Обсудить, подготовить и изменить материалы словами | Диалоги, результаты, задачи; настройки моделей по ссылке | /assistant |
| Аналитика | Оценить результат | Доставка, контент, аудитория при доступных API, расходы ИИ | /analytics |
| Настройки | Подключить и настроить | Проекты, соцсети, источники, модели ИИ, MCP и доступы, автоматизация, система | /settings |

Календарь — стартовая страница. Отдельной страницы «Обзор» в целевой навигации нет: полезные функции переходят в строку итогов, выбранный день и очередь внимания. Legacy /overview ведёт в календарь с фокусом на задачи после приёмки замены; пока старая страница остаётся доступной. Профиль и выход — меню аватара. Один постоянный CTA «+ Создать» открывает общий Composer. Уведомления и компактный статус системы не превращаются в дополнительные разделы.

Один выбранный проект действует на все рабочие экраны. «Все проекты» — режим обзора, а не объект-владелец материала. Создание требует явного projectId или ранее подтверждённого default. Deep link показывает фактический проект материала, не переписывает его. Смена фильтра не меняет активный run/черновик; глобальные настройки не фильтруются проектом. Общие assets явно обозначаются.

Первый запуск: не требовать подключения ИИ, соцсетей или облака до написания черновика. Можно начать с идеи, затем получить конкретные требования для отправки. Legacy /assistant.html, /projects, /socials, /sources, /schedule, /templates, /journal, /backups, /diagnostics сохраняют совместимые маршруты. Не ломать закладки, login return, back/forward. /mcp и /mcp/chatgpt не UI routes.

### 3.1.1 Повседневные сценарии

| Задача | Целевой путь |
|---|---|
| Быстрый пост | + Создать → текст/медиа/точные аккаунты → черновик или подтверждение плана/отправки |
| Идея на пятницу | Календарь → ячейка → идея → заметка → сохранить, без scheduler |
| Доработка | Карточка календаря → общий редактор → сохранить → прежняя дата и scroll |
| Серия материалов | ИИ → предлагаемый план → выбор строк и форматов → отдельные черновики |
| Ошибка | Календарь → «Требуют внимания» → конкретный материал/адресат → исправить или проверить результат |
| Сменить модель | ИИ/редактор → модель задачи; при отсутствии — точная ссылка в Настройки |
| Работа из ChatGPT | MCP → разрешённое действие → тот же материал/версия → approval владельца при необходимости |

Ни один базовый сценарий не проходит через технический экран, список шаблонов или обязательную настройку ИИ. При возврате сохранять дату, фильтры, scroll и проект. Один владелец состояния, один receipt, один главный CTA.

## 4. Стартовая рабочая доска: календарь + задачи

Не создавать второй Dashboard. На календаре одна строка «Сегодня N / На согласовании N / Ошибки N / Незапланировано N», без больших карточек. Нажатие открывает фильтр или инспектор соответствующих материалов. Счётчики измеряют материалы, результат по адресатам виден в деталях.

Инспектор выбранного дня опционален: время, название, формат, адресаты, причина состояния и главное действие. «Требуют внимания» — тот же инспектор в режиме проблем. Последние отправки доступны в списке и аналитике. Mobile: короткая строка итогов и день/неделя; инспектор — drawer. Пустой день предлагает добавить идею/публикацию.

## 5. Календарь — главный инструмент планирования

### 5.1 Экран

~~~text

[Проект: ASA Lab] [Площадки: Все ▾] [Форматы: Все ▾] [Статусы ▾]  [Часовой пояс ▾]
┌─ Пн ─────┬─ Вт ─────┬─ Ср ─────┬─ Чт ─────┬─ Пт ─────┬─ Сб ─────┬─ Вс ─────┐
│ 23       │ 24 +     │ 25       │ 26       │ 27       │ 28       │ 29       │
│ 10:00    │ 18:00    │ Идея     │          │ 12:00    │          │          │
│ Пост VK  │ Видео TG │ Shorts   │          │ Пост MAX │          │          │
│ Готов    │ Черновик │ Без медиа│          │ План     │          │          │
└──────────┴──────────┴──────────┴──────────┴──────────┴──────────┴──────────┘
[Незапланированные 5 ▾]                    [Выбранный день / детали →]
~~~

Неделя — рекомендуемый режим desktop при регулярном постинге, сохранять последний выбор. Месяц — обзор и плотные карточки: дата/время, формат (значок + подпись), краткий заголовок, платформы, статус, наличие ошибки. При переполнении «+ ещё N» раскрывает список дня, без растягивания сетки на весь экран. Неделя — временная сетка, день — полный список, список — табличная рабочая очередь с фильтрами. Пустой день + или клик по времени открывает тот же Composer с датой; кнопка «Добавить идею» в нем создаёт только редакционную запись, не задание scheduler. Незапланированные материалы в collapsible нижней области или drawer; не захламляют месячную сетку. Боковая панель показывает детали выбранной карточки и «Открыть редактор», а не второй редактор. Mobile по умолчанию список дня/недели с компактным календарём выбора даты; месяц доступен переключателем.

### 5.2 Данные и действия

- Различать идею на дату (редакционный план), черновик с желаемым временем и фактически авторизованную автоматическую отправку. Если доменная модель не сохраняет желаемое время без READY, использовать существующий безопасный draft AT metadata или отдельный согласованный additive field; не вводить фиктивную отправку. Идеи не исполняются scheduler.
- Дата, время и IANA timezone (проектный default; UI показывает локальное время и при необходимости UTC). Проверять прошлые даты, DST ambiguity и конфликтные слоты. Для разных независимых дат/форматов создавать отдельные связанные материалы либо отдельный утверждённый checkpoint per-target scheduling; не скрывать ограничение текущей модели.
- Перенос drag/drop с клавиатурной альтернативой «Перенести»; optimistic concurrency, версия, объяснение нового времени, повторный preflight/approval при material change READY. Показать «Отменить» только при безопасной обратной операции. Не перетаскивать опубликованные или активно отправляемые материалы; «Дублировать» создаёт новый черновик. При неуспехе возврат карточки на прежнее место.
- «Снять с публикации» прекращает будущую отправку по каноническому lifecycle, сохраняет материал; не удаляет внешний опубликованный пост. Повторяющийся контент создаёт отдельные черновики с явными получателями и временем; серия не активируется без owner policy.
- Правила очереди/повторения конфигурируются в Настройки → Автоматизация. В календаре только понятное «Следующий свободный слот» и результат, технические слоты не смешивать с публикациями.

### 5.3 Серии и варианты по площадкам

План может объединять связанные материалы: обычный пост VK/Telegram во вторник, вертикальный ролик в четверг, история в пятницу. Общий текст, бренд и assets переиспользуются, но каждый независимо отправляемый материал имеет собственный postId, время, kind и разрешение. Один post с несколькими target renditions допустим при одном времени и совместимом kind. Разные даты/форматы — отдельные связанные draft; не расширять неявно scheduler. Реальный group/series ID требует проверки домена и additive ADR; до реализации отображать только достоверные связи.

Календарь различает дату идеи, желаемое время черновика и подтверждённое время отправки. «План на неделю» сначала показывает редактируемую таблицу (дата, час, тема, формат, адресаты, необходимые материалы), выбор строк и проверку дублей. Apply идемпотентно создаёт только выбранные черновики, не активирует отправку. Повторяемые правила — отдельная настройка с паузой и журналом.

Desktop: форма 54–58% (min 480 при наличии места), предпросмотр 42–46%; независимая прокрутка содержимого, фиксированная нижняя панель. До первого сохранения доступны текст, медиа, точные получатели, действие — без обязательного wizard и бессмысленного заголовка. Название из первой содержательной строки; отдельное внутреннее название опционально. Формат по умолчанию «Пост»; автоматически вывести тип текста/фото/альбома/обычного видео, явно выбрать «Короткое видео» или «История» при доступной capability. Выбор конкретного аккаунта, не общий чекбокс бренда; «Выбрать получателей проекта» только явное действие. Дата в контексте календаря сохраняется при первом save. Поля без относящихся к формату опций скрыты. При доступной ширине редактора менее 1050 px использовать вкладки, не сжимать два поля до нечитаемости. На mobile вкладки «Редактировать / Предпросмотр» с общей сохранённой формой; нижняя панель доступна без пролистывания поста, вторичные действия в меню.

Функции: rich text, шаблоны, перетаскивание/порядок медиа (и кнопки вверх/вниз), импорт из медиатеки и облака, генерация через ИИ, просмотр фото/видео, cover/кадрирование/соотношение сторон если поддержано. Исходник не изменяется, производный asset сохраняется отдельно. Серверный preview resolver учитывает форматирование, caption, ограничения, разные получатели, overridden text/media order. Переключатель «Телефон/Компьютер» меняет только preview. Предпросмотр ориентировочный, не доказательство внешнего результата; неподдерживаемые элементы показывать предупреждением. Пользователь видит, что будет отправлено отдельно на каждом аккаунте.

ИИ внутри редактора — контекстные действия «Написать / Сократить / Адаптировать / Создать изображение / Подготовить видео». Показывать предложение и diff; «Применить» меняет только выбранный черновик/target, не отправляет. Генерация использует тот же job/asset pipeline, что чат и медиатека. Пока создаётся изображение, можно редактировать текст. Устаревший результат job не перезаписывает изменённый текст без явного применения.

Сохранение: локально видимое «Есть изменения / Сохраняем / Сохранено / Не удалось»; использовать versioned save и idempotency, черновик авто-сохранять только по согласованному механизму без READY/отправки. При конфликте 409 предложить обновить, сравнить, сохранить как отдельную копию; никогда молча не затирать изменения. При падении upload оставлять один восстановимый черновик с текстом и успешно добавленными медиа. Закрытие не теряет несохранённую работу без предупреждения.

Действия:
- «Сохранить черновик» не отправляет и не активирует расписание.
- «Запланировать» открывает точные дату/часовой пояс/получателей/предпросмотр, server preflight, затем owner confirmation либо approved policy. Ошибки рядом с адресатом и конкретное исправление.
- «Опубликовать сейчас» подтверждение точных адресатов и версии перед отправкой. После подтверждения durable receipt, прогресс по адресатам, итоговые ссылки. Не выдавать timeout за success; unknown outcome → ручное восстановление без автоматического повторного POST.
- «На согласование» / «Подтвердить» / «Отклонить» — различать редакционное принятие и разрешение отправки агента. Устаревший consent инвалидировать по действующим контрактам.
- Опубликованные/PARTIAL snapshots только просмотр истории, дублирование для правки будущих материалов. Изменение будущего READY сбрасывает готовность/требует проверки.

### 6.3 Тип публикации не равен типу файла

| Пользователь видит | Канонический kind/format | Особенности |
|---|---|---|
| Текстовый пост | FEED/TEXT_ONLY | Без обязательного изображения, если допускает конкретный adapter |
| Пост с фото | FEED/IMAGE | 1 фото |
| Альбом / карусель | FEED/CAROUSEL | Несколько вложений, mixed только по capability; порядок явный |
| Видео | FEED/VIDEO | Обычная видеопубликация, cover и параметры по adapter |
| Короткое видео (Shorts/Reels/Клипы) | SHORT/VERTICAL_VIDEO | 9:16 как рабочий preset, платформенные ограничения проверяются сервером |
| История / Stories | STORY/IMAGE, STORY/VERTICAL_VIDEO, STORY/STORY_SEQUENCE | Медиа/кадры в порядке, отдельная live capability для каждого вида |

Сохранять возможность подготовить материал/экспортировать файл даже при отсутствии adapter. Не показывать кнопку отправки как доступную, если формат не подтверждён. Нельзя silently заменить Story/Short обычным постом. Если разные форматы требуют разных публикаций, создать связанные черновики с явным выбором, не терять один из них.

### 6.4 Площадки и доступность

Текущее статическое объявление src/platforms/capabilities.ts на baseline: Telegram/VK/MAX FEED text/image/video/carousel/mixed; Instagram FEED image/carousel. Все четыре объявляют supportsStories=false и supportsShortVideo=false. Это только объявление адаптера, не гарантия live; отдельные story/short экспериментальные пути и документы не равны разрешённой отправке. Итог строить по текущей серверной композиции + credential/destination profile + live release gate + lifecycle/approval.

| Площадка | Целевая продуктовая потребность | Стартовое решение |
|---|---|---|
| Telegram | Текст, фото, альбом, видео, истории | FEED использовать при verified capability; истории отдельный checkpoint |
| VK | Текст, фото, альбом, видео, клипы/истории | FEED проверять права фото/видео отдельно; клипы/истории не включать до официального API и live acceptance |
| MAX | Текст, фото, альбом, видео; другие форматы при появлении API | FEED capability; не обещать нативные stories/shorts |
| Instagram | Фото, карусель, видео/Reels/Stories | Подтверждённые текущие форматы; остальные отдельно проверять |
| YouTube | Видео, Shorts | Новый adapter-кандидат, отдельное OAuth/capability/API/live acceptance; не обещать наличие в первом выпуске |

Не жестко кодировать лимиты в UI; сервер возвращает совместимость каждого конкретного адресата. Для неподдерживаемых вариантов: «Можно подготовить, автопубликация недоступна» + причина/действие. Новые площадки — не условие начала UX-работ.

### 6.5 Подтверждение и единое действие

Нижняя панель: один главный CTA по текущему намерению («Сохранить идею», «Сохранить черновик», «Запланировать», «Подтвердить отправку»). Черновик — вторичное действие, остальные в меню. Перед отправкой/активацией расписания: компактная сводка проекта, точной версии, текста/медиа, каждого адресата/формата, даты/часового пояса, режима согласования. Недоступный адресат не удаляется автоматически: исправить или снять выбор явно. Стоимость генерации подтверждается отдельно.

Ошибки разделить: редакционный недочёт, формат, credential, сеть, запрещённое действие, неизвестный результат. «Исправить» ведёт к конкретному полю/подключению и возвращает в редактор. Успешный/unknown target не повторяется автоматически.

Сценарии:
- «Составь план на 7 дней» → предложенные идеи/даты, preview списка; после явного разрешённого действия создаются отдельные draft/idea с versioned receipts.
- «Напиши пост о робототехнике и создай картинку 4:5» → текст + job изображения, выбор результата → один черновик → открыть тот же Composer.
- «Сделай 30-секундный ролик/Shorts» → сценарий, кадры/промпты, доступный video generator либо импорт/монтаж внешнего результата; если генератор отсутствует, явно только сценарий/подготовка.
- «Перенеси завтрашние посты на вечер» → точный список/новые даты/часовой пояс, разрешённое изменение с версиями и повторное согласование при необходимости.
- «Проверь, что не отправилось» → фактические статусы/ошибки/безопасные действия, никаких придуманных ссылок.
- «Публикуй по правилам» → предложение политики, owner confirmation, отдельный execution gate. Чат не подтверждает собственную заявку.

Инструменты и результаты: сообщение модели не является выполненным действием. Каждая операция показывает понятное имя, объект/адресатов, состояние, фактический server receipt, ошибку и «Открыть». Только чтение — без инструментов записи; текущий per-model режим и per-message allowWrites сохраняются, новые действия требуют их effective intersection. Не превращать чат в административный shell. Не сохранять и не показывать скрытые рассуждения; журналировать только внешние действия/события. Ошибка/таймаут не отменяет уже подтверждённый результат; серверная проверка receipt перед повтором.

### 8.1 Модели, генераторы и маршрутизация

Разделить **подключение к провайдеру** (endpoint, credential, network policy) и **назначение модели** (text/chat, vision, image generation, video generation; audio/transcription optional future). Не выдавать обычный LLM за генератор изображений. Один провайдер может иметь несколько моделей и разных capabilities. Назначения проекта: модель текста, изображений, видео, optional default; ручной override перед запуском. Не переключать на платного провайдера без явной настройки и согласия.

- Существующий текстовый контур: Ollama, llama.cpp, OpenAI, DeepSeek, OpenAI-compatible. Локальный Ollama/llama.cpp и облачный endpoint имеют разные network policies; отдельные локальные адреса сохраняются отдельно.
- Новые генераторы: сначала проверить существующие возможности и поддерживаемые API, предложить локальный image provider (например, ComfyUI при наличии настроенного сервера и проверенного workflow), облачный image API и video API по конкретному adapter. Не обещать поддержку провайдера по названию; каждый adapter проходит capability/security/real test. Не выполнять произвольный workflow/URL от модели без владельца.
- «Проверить и сохранить»: обнаружение моделей, тест текстового ответа, тест harmless tool call отдельно (модель может отвечать, но не вызывать tools), тест генерации отдельно с явно указанной стоимостью/ресурсами и разрешением; network/TLS/auth/quota/model unavailable/tool unsupported ясно разделены. Не заменять ранее работающую запись при неудачном редактировании; статус последней проверки и её время, не «онлайн» на основании старого теста.
- Job lifecycle для изображений/видео: принято → в очереди → выполняется → результат проверен/добавлен → ошибка/отменено. Стойкий ID, timeout, polling/reconnect, idempotency, защита от двойного платного запроса; хранить безопасные provider receipts. При неизвестном результате платного вызова не повторять вслепую. Прогресс показывать только если источник его реально сообщает. Отделить генерацию от публикационного scheduler; сохранять существующий модульный монолит до отдельного ADR.
- Реальные assets: MIME/size/duration validation, canonical storage/ACL, preview, provenance (модель, параметры, время, исходники), выбор результата владельцем или разрешённой политикой. Не отправлять приватные материалы внешнему провайдеру без разрешённого доступа.
- Расходы: если провайдер возвращает usage/цену — записать подтверждённые величины, отдельно показывать оценку; если нет — «нет данных». Лимиты/дневной бюджет и явный контроль платной генерации. Секреты шифровать и не возвращать модели/браузеру. Для локальных моделей не выдумывать стоимость токена.

### 8.2 Настройки по задаче, а не по названию провайдера

Первый экран — таблица «Задача / Назначенная модель / Последняя проверка / Действие»: текст, изображение, видео, анализ файлов. Неназначенная задача — одна кнопка «Подключить». «Все подключения» — управление несколькими серверами и ключами, расширенные параметры по запросу. Мастер: тип локально/облако → provider → адрес/ключ → список моделей → тест → сохранить → назначить задаче. Для текста отдельно «Ответ модели» и «Вызов инструментов Publikator». Нельзя показывать «Подключено» только потому, что сохранён ключ.

Тест выполняется из контейнера. DNS/маршрут/таймаут, 401/403, quota, несовместимый endpoint, отсутствующие tool calls и отсутствующий генератор — разные сообщения с конкретным следующим шагом. Не стирать рабочее подключение при неудачном тесте новой записи. Наличие Ollama на другом компьютере не доказывает доступность из контейнера. Кандидаты: ComfyUI с проверенным workflow; OpenRouter/Polza AI — только после официальной проверки API, credential и capability, не как готовые интеграции. Никаких произвольных URL от модели, платного fallback без согласия.

### 8.3 Длительные задачи

Один компактный список задач/уведомлений: выполняется, завершено, требуется действие, ошибка. Стойкий jobId/receipt, проект/черновик, модель, время, бюджет, фактическое состояние. Закрытие чата/смена проекта не отменяет подтверждённый job и не переносит результат в другой проект. «Открыть результат» ведёт к asset/черновику. Отмена только если поддерживается; проценты только из реальной информации. Retention/backup метаданных; без distributed worker без ADR.

## 9. Внешний MCP — полноценное рабочее управление

Общий бизнес-контур: Web UI / внутренний assistant / внешний MCP → canonical services + ACL/preflight/version/approval → SQLite/media → один publisher/scheduler. Не делать отдельный REST/MCP publisher. OAuth /mcp/chatgpt для scoped внешних клиентов; owner-issued bearer /mcp для отдельно доверенных клиентов. Совместимые MCP-клиенты проверять по фактическому транспорту/авторизации, не гарантировать работу с любым чатом без acceptance.

| Группа функций | Что должен уметь внешний клиент после принятия соответствующего этапа |
|---|---|
| Чтение | Проекты, аккаунты с effective capability, календарь с фильтрами, публикации, ошибки, медиа/источники, доступные модели/параметры, delivery/analytics |
| Создание | Идеи/черновики, rich text, формат, явные recipients, версия, медиа (папки/файлы/upload), производные assets |
| Генерация | Запросить текст/изображение/видео через разрешённый provider, job status/cancel, получить asset ID и preview; не получать secret |
| Редактура | Версионированная правка, порядок, per-target overrides, duplicate, archive/restore по lifecycle; конфликт возвращает current version и безопасное действие |
| Предпросмотр/планирование | Server preview/preflight, подготовка точного времени/очереди, запрос immutable publication intent |
| Отправка | Владелец утверждает точную revision/recipients/time; после gates policy разрешает автоматическую отправку. Receipt/status по каждому адресату; revoke блокирует новые claims |
| Журнал | Фактические операции, jobs, error remediation и links, запрос состояния без доступа к чужим ресурсам |

Это целевой каталог групп, не перечень уже зарегистрированных tools и не разрешение на одномоментное расширение scopes. На baseline внешний ChatGPT реально имеет 11 инструментов (projects/accounts, create/list/get/edit text drafts, list/get publications, delivery analytics, list sources, attach cloud media). #268/#269 не в main. Сначала завершить существующий контракт A4/A5a/A7/A5b с согласованием схем и owner gate; потом расширять генерацию/редактуру на общих сервисах. Старые tools, идентификаторы, idempotency и API compatibility сохранять; новые capability tools объявлять только если реализованы и разрешены. Для каждого нового инструмента — typed schema, readOnly/destructive/idempotent annotations, bounded result, pagination, resource grant, optimistic concurrency, error contract, audit и test. Подтверждение внутри внешнего UI само по себе не доказательство owner consent серверу.

Новые подключения по действующему контракту: OBSERVER + DRAFT_ONLY + пустые allowlists. Уровни Observer/Limited/Extended/Full content/Custom и отдельно режим «Не публиковать / После моего подтверждения / По моим правилам»; effective access = scopes ∩ конкретные ресурсы ∩ verified platform capability ∩ lifecycle ∩ consent/policy. Новый tool/аккаунт не расширяет старый grant. Отдельные права на генераторы и затраты, на конкретные проекты/аккаунты/источники. Сохранить существующий OAuth refresh/PKCE и #287 отдельно; не принуждать к relink при редизайне.

### 11.1 Автоматизация без скрытых действий

Раздельные результаты: подготовка черновиков, генерация медиа, отправка. Не объединять одним флажком. Пример: воскресенье — семь идей → выбранные черновики → генерация по бюджету → согласование → отправка. Сводка правила: проект, источники, модели, конкретные аккаунты, лимиты материалов/затрат, часовой пояс, срок/expiry, режим согласования. Preview правила не вызывает платный API и не отправляет. Pause прекращает новые запуски; судьба активных/одобренных операций объясняется по действующим контрактам.

## 12. Единые статусы и безопасность

Сохранить две независимые state machines VNEXT §4. UI может показывать производную метку «Идея», «Черновик», «На согласовании», «Запланировано», «Отправляется», «Опубликовано», «Частично», «Ошибка», «Нужно проверить результат», «Архив», но не записывать выдуманный DB enum. «Запланировано» означает проверенный и разрешённый scheduler intent; у неактивного draft с датой — «Планируется, не отправится автоматически». «Готово» (READY) не означает owner approval агента. На карточке отдельно дата/редакционный статус/доставка по получателям. Состояние recovery имеет отдельное объяснение и ручное действие без unsafe retry. Никаких зелёных статусов до фактического сервера.

| Состояние UI | Значение | Действие |
|---|---|---|
| Идея | Редакционный план, не исполняется | Подготовить |
| Черновик / Планируется | Сохранён, дата желаемая, отправка не активна | Редактировать |
| На согласовании | Ожидается точное решение владельца | Проверить |
| Запланировано | READY revision, расписание и нужная авторизация | Перенести / снять с плана |
| Отправляется | Есть активный claim | Посмотреть статус |
| Опубликовано | Подтверждённый внешний результат | Открыть ссылку |
| Частично / Ошибка | Разные результаты target или известный отказ | Открыть адресаты |
| Нужно проверить результат | Неизвестный исход внешнего POST | Проверить вручную |
| Архив / Корзина | Не участвует в будущей отправке | Восстановить по lifecycle |

Это правила представления, не новая enum/state machine; legacy состояния не маскировать.

Server-authoritative версия/immutable ready snapshot, exact recipients/credential fingerprints, preflight при READY и перед claim, idempotency, unknown outcome recovery, canonical backup/restore, AES credentials, SSRF protection, current grants, audit. Медиа/данные приватны, внешние генераторы и MCP видят только разрешённое. Все серверные изменения через GitHub/CI; runtime операции через существующий 1Panel, после backup/release checks. Не добавлять Redis/worker farm/новую DB без ADR. Не переносить внутренние админские возможности к обычному внешнему OAuth клиенту.

Этапы обозначают логическую программу; большой этап P2-04/08/09 дробится на независимые checkpoint PR. Не выполнять сразу все задачи. Контроллер согласует очередность/область с владельцем, распределяет независимые задачи и проверяет handoff, избегает параллельных правок общих компонентов. Перед каждым этапом прочитать AGENTS и целевой раздел, свежий main, зависимые issues/PR. По существующим ограничениям, schema migration, security, CI, backup/restore — текущие нормативные требования.

### 13.1 Пользовательские выпуски

Не ждать всех этапов. Контроллер фиксирует самостоятельные delivery gates; каждый release проходит CI, backup/rollback и согласованное развёртывание.
- R1 «Ежедневная работа» — P2-01/02/03 + необходимые части P2-04: календарь, общий редактор, существующие аккаунты и медиа, ручной цикл целиком на тестовом адресате. Не выпускать пустую оболочку.
- R2 «ИИ работает» — P2-05/06/07A + необходимые jobs: реальные текстовые модели и одна проверенная генерация изображения в том же черновике.
- R3 «Управление извне» — P2-08A/B и safety gates: внешний ChatGPT читает, готовит, прикрепляет, показывает preview и запрашивает согласование в общем контуре. Развивать независимо от CSS после стабилизации контрактов.
- R4 «Видео и масштабирование» — P2-07B/09/10/11 по подтверждённым платформам, автоматизация и фактическая аналитика.

Не удалять legacy путь, пока новый не принят. Не закрывать #287 вследствие UI релиза.

## 15. Решения, которые предлагается принять владельцу

1. Пять рабочих разделов + Настройки, календарь вместо Обзора, проектный контекст везде, один постоянный CTA.
2. Один универсальный Composer и один бизнес-контур для UI, внутреннего чата и внешнего MCP.
3. Чат с управлением контентом; модели для текста, изображения и видео настраиваются отдельно по фактической capability. Локальные и облачные варианты, без автоматической смены провайдера/платных расходов.
4. Все форматы можно готовить как материалы; реальная отправка появляется только при доказанной поддержке конкретной соцсети и адресата. YouTube — кандидат отдельного adapter.
5. Публикация ИИ по умолчанию не разрешена; владелец подтверждает конкретную публикацию или явную ограниченную auto-policy.
6. Сохранить монолит, SQLite, данные, scheduler, publisher, backup, existing ACL/OAuth; улучшать через небольшие PR, не новый продукт поверх старого.
7. Проверить интерактивный прототип, согласовать P2-00, затем законченный выпуск R1. Не начинать все экраны одновременно.

**Definition of Done этого документационного checkpoint:** продуктовая модель и компоновки доступны в GitHub, точные ссылки и baseline известны; владелец принимает или корректирует предложение, независимое ревью и обязательный CI пройдены перед merge. Это не означает, что Publikator 2.0 реализован или установлен.
