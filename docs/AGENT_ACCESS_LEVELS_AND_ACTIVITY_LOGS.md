## 1. Цель владельца и видимый результат

Владелец подключает ChatGPT, Claude, Codex, n8n, Telegram/другой бот, видит **понятный уровень возможностей**, выбирает разрешённые проекты/аккаунты/источники, назначает правила отправки, видит текущую работу и подробную историю. Например:

> «ChatGPT — ASA Lab» · **Ограниченный** · Проект: ASA Lab · Источник: ASA Lab VK в Google Drive · Площадки: VK «Основная группа», Telegram «ASA Lab» · **Публикация запрещена без моего подтверждения** · Последняя операция: «Создан черновик», 14:37.

Должно быть ясно, **что именно бот может сделать; чего не может; что делал; что делает сейчас; почему остановлен; что опубликовано фактически**. Пользователь не обязан разбираться в scopes, `READY`, `ContentRevision`, OAuth, JSON-RPC или статусах SQLite.

Критично: **журнал фиксирует фактические серверные вызовы, состояние заданий и результаты**, а не скрытые рассуждения модели, непроверенные обещания агента или выдуманные сообщения о прогрессе. Нет обязанности и права записывать приватные рассуждения ИИ («chain of thought»).

## 2. Один механизм прав, два независимых измерения

### 2.1 Уровень возможностей (операционный preset)

Уровень — **именованный снимок разрешённых операций/scopes**, а не токен, не capability площадки и не разрешение публиковать куда угодно.

| Отображение | Стабильный preset ID | Что может | Чего не может |
|---|---|---|---|
| **Наблюдатель** · Только просмотр | `OBSERVER` | Читает разрешённые проекты, публикации, безопасные сведения об источниках/аккаунтах и статусы **своих** заданий | Не создаёт и не изменяет черновики, медиа, расписание, публикации |
| **Ограниченный** · Подготовка материалов | `LIMITED` | Всё из «Наблюдателя» + выбор/импорт медиа, подготовка и правка разрешённых черновиков, предпросмотр, запрос согласования | Не назначает самостоятельную автоматическую отправку, не выполняет публикацию |
| **Расширенный** · Планирование с подтверждением | `EXTENDED` | Всё из «Ограниченного» + подготовка точного времени/очереди и запрос на публикацию после подтверждения владельца | Не публикует автоматически без индивидуального owner consent |
| **Полный** · Управление публикациями | `FULL_CONTENT` | Все **неадминистративные** контент-операции в явно разрешённых проектах и аккаунтах; можно настроить автоматизацию по заранее утверждённой owner policy | Не получает админ-пароль, социальные токены, 1Panel/GitHub, управление правами других ботов; не подтверждает собственные материалы |
| **Свой набор** · Индивидуальные права | `CUSTOM` | Отмеченный владельцем точный subset scopes с ограничениями | Не может превысить полномочия разрешённого owner policy или обойти защищённые действия |

**MUST:** два уровня, имеющие одинаковые effective permissions, не должны различаться серверной логикой из-за русской подписи. A0 закрепляет точную map `presetId → scopes` в versioned JSON Schema и тестирует её против OpenAPI/MCP. `FULL_CONTENT` включается **только явным выбором владельца**, не является дефолтом.

**Важно различать:** агентский «Полный» (`FULL_CONTENT`) — это **не** социальный `CapabilityProfile accessLevel=FULL`. Даже самый полномочный бот не может отправить фото в VK, если конкретный credential/destination не имеет соответствующих проверенных provider rights. Итоговая возможность = scopes ∩ grants ∩ verified capability ∩ approval/policy ∩ lifecycle.

**Сохранённые presets версионируются:** `presetId`, `presetVersion` и точный snapshot scopes. Добавление новых функций в версию продукта **не расширяет автоматически** права ранее подключённого бота; для новых scopes требуется явное обновление grant владельцем.

### 2.2 Режим отправки (отдельная настройка, не дублирующая preset)

| Режим UI | ID | Поведение |
|---|---|---|
| **Не публиковать** | `DRAFT_ONLY` | Только черновики и предпросмотр; никакой `READY/approve` сам по себе не разрешает POST |
| **Только после моего подтверждения** | `OWNER_APPROVAL` | Бот формирует immutable PublicationIntent; владелец видит точные текст, фото, порядок, аккаунты и время, затем утверждает или отклоняет |
| **Автоматически по моим правилам** | `PREAPPROVED_POLICY` | Требует `FULL_CONTENT` либо `CUSTOM` с эквивалентными scopes и явной отдельной owner-approved policy: проекты, аккаунты, форматы, источники, лимиты, время, срок действия |

**Default для нового бота:** `OBSERVER` + `DRAFT_ONLY` + пустые allowlists (пока владелец не выбрал ресурсы). UI может предложить «Ограниченный», но самостоятельно не включать `publish:request` или автоматизацию. `OWNER_APPROVAL` и `PREAPPROVED_POLICY` не предоставляют scopes, которых нет в пресете.

**MUST:** при `FULL_CONTENT + OWNER_APPROVAL` отдельная отправка допускается **после** индивидуального owner consent на точный intent; `PREAPPROVED_POLICY` нужна для заранее согласованной *автоматической* отправки без подтверждения каждого поста. 

**MUST:** «Полный» не означает «публиковать без спроса». В интерфейсе в одной строке показывать **Уровень: Полный · Отправка: После подтверждения** или **Уровень: Полный · Отправка: По правилам [показать правила]**. Если владелец выбрал `EXTENDED`, переключатель автоматизации недоступен с точным объяснением. Срок/количество действия auto-policy не может быть бесконечным неявно.

### 2.3 Область доступа к ресурсам

В каждой карточке бота выбирать **конкретные** `projectId[]`, `accountId[]`, `sourceConnectorId[]`/разрешённые папки Google Drive. По умолчанию пусто. Чекбокс «Все текущие аккаунты» допустим только после отдельного подтверждения: сохраняет **снимок текущих IDs**, не wildcard на будущие подключения. Новые аккаунты не наследуются автоматически.

Матрица эффективного доступа показывает возле аккаунта `«Текст: можно»`, `«Фото: нельзя — нужен пользовательский ключ VK»` с реальными `CapabilityProfile` данными. В случае недостаточных прав необходим точный текст исправления.

Для `CUSTOM` разрешены granular scopes по группам: «Чтение», «Медиа», «Черновики», «Предпросмотр», «Согласование», «Расписание», «Запрос публикации», «Статусы». Административная настройка API-токенов, OAuth clients, других AgentGrants и секретов **не является выбираемым scope** у обычного бота.

При изменении preset, списка ресурсов, режима или квоты:
- владелец сначала видит `«Было → Станет»` и какие новые операции станут доступны;
- сервер проверяет `expectedGrantVersion`, сохраняет новую `grantVersion` атомарно с audit event, сразу пересчитывает effective ACL;
- уже выданный bearer не получает расширение до нового owner consent; сервер заново проверяет current grant по каждому запросу;
- pending/scheduled agent-managed intents при изменении прав перепроверяются перед отправкой; устаревший consent инвалидируется по правилам `UNIVERSAL_AGENT_API_MCP_SPEC.md` `16.2`;
- отзыв блокирует **новые** execution claims после commit; уже вызванный provider может завершить отправку, что показывается честно.

## 3. Пользовательские экраны

### 3.1 `Настройки → ИИ и API → Подключённые боты`

Для каждого бота:

```text
ChatGPT · ASA Lab                        Подключён
Полномочия: Ограниченный                  Отправка: Только с моего согласия
Проекты: ASA Lab                          Аккаунты: VK / Telegram (2)
Последнее действие: 14:37 · Создан черновик «Arduino — урок 5»
Сейчас: Ожидает вашего подтверждения     [Посмотреть действия]
[Настроить доступ] [Приостановить] [Отозвать доступ]
```

Показывать `name`, `clientKind`, статус подключения/токена/политики, выбранный preset и режим, exact count ресурсов, `lastSeenAt`, последнюю **подтверждённую сервером** операцию и состояние текущего `jobId`.

Различать `ONLINE/CONNECTED` (авторизация работает), `INACTIVE` (не было вызовов), `RUNNING` (серверное задание действительно выполняется), `WAITING_APPROVAL`, `PAUSED`, `REVOKED`, `NEEDS_ATTENTION`. Не утверждать «бот сейчас думает» на основании открытого OAuth или давнего подключения. Доступность модели и фактическая обработка запроса вне Publikator могут быть неизвестны серверу.

### 3.2 `Карточка бота → Возможности`

- Радиокарточки **Наблюдатель / Ограниченный / Расширенный / Полный / Свой набор** с коротким описанием и явным «Может / Не может».
- `«К каким материалам есть доступ»` — конкретные проекты, источники и папки.
- `«Куда можно публиковать»` — конкретные аккаунты с platform capability verdict.
- `«Когда разрешено публиковать»` — запрет / после согласования / по правилам.
- Для auto-policy отдельные поля: часовой пояс, разрешённые дни/часы, число публикаций за день, допустимые форматы, срок истечения; `«Сохранить правила»` только после явного owner confirmation.
- Сверху обычное текстовое резюме: `«Этот бот может создавать черновики и загружать фото в проект ASA Lab, но не может отправлять публикации без вашего подтверждения»`.

При сохранении показывать подтверждение повышения привилегий; при понижении — эффект на ожидающие задания. Владелец может `«Сделать копию настроек»` (без дублирования bearer/refresh secrets), `«Приостановить»` и `«Отозвать»`. Отзыв описывает неопределённость in-flight отправок.

### 3.3 `Карточка бота → Сейчас` и `История действий`

**Цель:** пользователь видит, что именно делает приложение по команде конкретного бота.

Пример **иллюстративной**, не реальной истории:

```text
14:35:01  ChatGPT · Запросил список разрешённых материалов      Выполнено
14:35:04  ChatGPT · Выбрал 3 изображения из Google Drive      Выполнено
14:35:06  Publikator · Обрабатывает фотографии (2 из 3)     Выполняется
14:35:08  Publikator · Сохранил изображения и порядок       Выполнено
14:35:10  ChatGPT · Создал черновик «Курс Arduino»          Выполнено
14:35:12  ChatGPT · Отправил материал на согласование      Ожидает владельца
14:38:21  Владелец · Подтвердил точный пост и 2 аккаунта   Одобрено
14:39:02  Publikator · VK «ASA Lab»: пост опубликован       Ссылка на VK
14:39:03  Publikator · Telegram: результат не подтверждён  Требуется проверка
```

**Не** выводить сообщения «Выполнено», пока сервер не подтвердил соответствующий результат. Локальные браузерные действия без сервера показываются как transient UI progress и не становятся audit evidence. Вся логика публикации/ошибок остаётся в canonical domain.

В режиме «Сейчас» показать:
- `jobId`/заголовок работы, начато/последнее обновление;
- статус `RUNNING` / `WAITING_APPROVAL` / `SCHEDULED` / `SUCCEEDED` / `PARTIAL` / `FAILED` / `RECOVERY_NEEDED`;
- последнее подтверждённое server stage и численный прогресс **только если известны общий объём и завершённые единицы**;
- связанные post, project и конкретные targets; кнопка «Открыть публикацию»;
- предложение владельцу при `NEEDS_ATTENTION` (согласовать, проверить аккаунт, открыть журнальные данные).

Если запрос MCP уже завершён, но публикация только назначена, писать `«Запланировано»`, а не `«Бот работает»`.

Обновление списка: bounded polling с курсором (рекомендуемый UI-интервал при открытой вкладке 3–5 сек, при отсутствии активности реже; при ошибках backoff) или server event stream, **без нового worker/broker**. Ни одна фоновая проверка UI не должна порождать audit event «бот запросил».

Для P0 обязательно: карточка агента, сохранение уровня/ресурсов/режима, `«Сейчас»`, последние события с пагинацией, owner approval action, пауза/отзыв и базовые фильтры. Для P1: расширенный поиск, группировка сессий, отчёты, экспорт и Webhooks.

### 3.4 `Журнал` (существующий раздел приложения)

Не создавать конкурирующую историю событий. Использовать canonical audit/event source и отобразить в существующем `Журнал` фильтр `«Боты»` с параметрами `агент / проект / период / статус / тип операции / аккаунт`. По клику открывать те же details, что в карточке бота, с bounded URL и проверкой owner auth. `«Журнал бота»` — scoped представление одного источника, не отдельная автономная БД или массив JS.

### 3.5 Мобильный интерфейс

320/390 px: компактные карточки, вертикальная история, теги статуса, фильтры в раскрывающейся панели; без горизонтального скролла и бесконечных длинных URL. Desktop: плотная таблица с сортировкой и drawer деталей. Нужны клавиатурные действия, focus, screen-reader labels, touch targets и текстовые/иконные обозначения (цвет никогда не единственный признак). В форме разрешений 11+ аккаунтов — поиск, группы по платформам, точные чекбоксы.

## 4. Модель журнала — server-authoritative, durable

### 4.1 Понятные данные для каждой операции

`AgentActivityEvent`/эквивалент в SQLite:

- `eventId`, `schemaVersion`, монотонный `sequence`, `occurredAtUtc`;
- `actorType` = AGENT / OWNER / SYSTEM; `agentId`, `clientKind`, `displayName` без секретов;
- `origin` = MCP / REST / UI / SCHEDULER / RECOVERY;
- `requestId`, `correlationId`, `operationId`, `jobId?`, `postId?`, `projectId?`;
- bounded `targetAccountIds[]` / safe target names, `mediaCount?`, `revisedContentVersion?`;
- `stage` = REQUESTED / AUTHORIZED / STARTED / PROGRESS / WAITING_APPROVAL / SCHEDULED / COMPLETED / FAILED / DENIED / RECOVERY_NEEDED / POLICY_CHANGED;
- `outcome`, safe `errorCode?`, safe `remediation?`, `durationMs?`, `grantVersion?`, `publicationIntentId?`;
- `safeSummary` формируется серверным словарём шаблонов на основе реально записанной операции, не из свободного AI-текста.

Каждое существенное изменение policy/выдача и отзыв токена/запрос согласования/owner approval/denial/подготовка задания/внешний publish start, result, recovery должно оставлять долговременную запись. Для high-frequency reads полезна **агрегация или rate-limited sampling** без подавления важных denied/security actions. Отдельные события “progress” создавать при реальном переходе `job`, не каждую секунду.

**Запрет:** лог действий не является записью внутренних мыслей/промптов ИИ. Не обещать человеку «видеть мысли бота». Допускается только проверяемая активность Publikator.

### 4.2 Кто видит журнал и что скрыто

Владелец (authenticated single-admin session) видит логи всех подключённых агентов и их собственные административные изменения. Сам агент может прочитать только **свои** job/status events при наличии `jobs:read/events:read`, с фильтрацией по grant; остальные боты/токены/grants/сообщения и исходные медиа — недоступны.

**Не хранить в audit даже временно:** raw Bearer/refresh/API tokens, Google Service Account JSON/private key, `APP_MASTER_KEY`, cookies, Authorization header, приватные полные тело запроса/промпты/исходные media bytes, query parameters с секретами, подробные stack traces. Redaction/minimization MUST выполняться **до записи в SQLite**, а не только при чтении; test fixtures с canary secrets и повторной проверкой backup/export.

`safeSummary` не копирует целиком текст публикации и не хранит имена файлов с приватными путями; показываются post title/id и ссылка на авторизованный просмотр. Доступ к оригинальным media/preview остаётся за ACL. Текст ошибки от провайдера проходит sanitization и stable error codes (`IP_RESTRICTED`, `PERMISSIONS_DENIED`, `REVIEW_REQUIRED`, `RECOVERY_NEEDED` и др.).

### 4.3 Сохранность, поиск и retention

- `append-only` audit по смыслу: агент не может редактировать или удалять события. Удаление старых событий только через отдельную owner retention policy, без изменения опубликованной истории.
- Полная публикационная история, immutable owner approvals и provider outcomes должны переживать canonical SQLite+media backup/restore. Указанные critical receipts хранятся с lifecycle публикации, а не очищаются раньше неё.
- Для операционных non-critical событий предложить default retention **90 дней** (A0 согласует с существующей policy `docs/RELEASE_MIGRATION_POLICY.md`/настройками); пользователь видит срок и может менять в безопасных пределах. Не удалять события о спорных/неопределённых исходах.
- Индексы по `agentId, occurredAtUtc`, `jobId`, `postId`, `eventId`; pagination by stable cursor/sequence, bounded payload and page size. При большом объёме UI не загружает всю таблицу в память.
- Успешное approval/revoke/claim должно фиксироваться **атомарно** с соответствующим событием либо отказать fail-closed; менее критичный read telemetry не должен срывать работу приложения из-за временного отсутствия вспомогательного журнала (но обязан оставить безопасный диагностический признак).
- Журнал не самотестирует продукт: in CI проверять фактические эффекты/состояния БД и fake-provider call count отдельно от красивого текста истории.

## 5. Минимальные серверные контракты

Единая Application Service для `AgentGrant` + `AgentAudit`, без отдельного permission engine для Web UI и MCP.

**Owner-only endpoints (конкретные пути утвердить на A0, ниже — концептуальный список):**
- list/read agent principal and effective permissions;
- preview draft grant change (before/after + new rights);
- create/update grant with `expectedGrantVersion` + owner re-confirmation;
- pause/resume/revoke agent;
- list agent activity with filters/page cursor and safe details;
- get current active jobs/approval queue and per-target statuses.

Owner UI авторизован через existing admin session + origin/CSRF; агент **не** может вызвать эти методы с собственным bearer. Agent API продолжает использовать scopes/grants, не наследует право управлять своими полномочиями.

**P0 query contract:** возвращать `effectivePresetId`, `effectiveScopeIds[]`, `publishMode`, `projectIds[]`, `accountIds[]`, `sourceConnectorIds[]`, `grantVersion`, `policyExpiresAt`, `lastUsedAt`, `activeJobSummary?`, `recentActivity[]` и safe `blockedReasons[]`. Никаких decrypted credentials.

**Audit/event APIs:** seek pagination/filter per agent/owner and `GET /api/agent/v1/jobs/:id` scoped by grant. REST/MCP read-only methods MUST have zero DB/media mutations; existing `GET /api/posts/:id` with `ensureTargets` is **не** допустимый implementation pattern для Agent API.

## 7. Definition of Done

Функция готова, только если:
1. Владелец настраивает бот **без знания технических scopes** и видит эффект для конкретных проектов, источников и аккаунтов.
2. Backend обеспечивает ровно те же права, что написаны в UI, в том числе после рестарта и при конкурентных изменениях.
3. Видны реальные события и задания; failed/denied/unknown состояния не выглядят успешными.
4. Есть возможность приостановить и отозвать доступ; инциденты расследуются через requestId/jobId/post/target trace.
5. Данные/ключи не попадают в логи, результаты MCP и экспорты; owner/admin видит только разрешённое.
6. Canonical migration/backup/restore, browser/UI, API/MCP и fake-provider acceptance доказаны на точном SHA; при изменении HEAD проверки и ревью повторены.

Данный документ — **план и контракт**, не утверждение, что настройки, OAuth/MCP и журнал уже реализованы или работают на установленной машине.
